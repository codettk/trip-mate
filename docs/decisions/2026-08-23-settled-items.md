# "이미 정산함" — 금액을 남긴 채 계산에서만 빼는 세 번째 상태

2026-08-23. 사용자 요청: **"정산 금액을 적어놨는데, 각 건별로 돈은 적어야되고, 정산 완료를 선택하게 해서 정산 금액에서는 빠지게 하고 싶어"**

## 왜 지금까지 방법이 없었는가

현장에서는 **결제한 그 자리에서 바로 나눠 내는** 일이 흔하다. 그런 지출도 "우리가 이 여행에서
얼마 썼는지"에는 들어가야 하지만, 정산 계산에는 들어가면 안 된다. 그때까지 방법이 둘뿐이었다.

| 방법 | 무슨 일이 벌어지는가 |
|---|---|
| `split = false` (정산 제외) | 금액·결제자·대상을 **DB 에서 실제로 비운다.** 얼마 썼는지가 사라진다 |
| 그냥 둔다 | 이미 주고받았는데 이체 목록에 계속 남는다. **정산이 영원히 마감되지 않는다** |

둘 다 답이 아니다. 앞은 기록을 잃고, 뒤는 끝나지 않는다.

## 정한 것 — `Item.settled`

**금액·결제자·정산 대상을 그대로 둔 채, 계산에서만 뺀다.**

```
split=false  →  금액 자체가 없다        (cost 0 · payer null · 대상 없음)
settled=true →  금액이 살아 있다        (계산에서만 빠진다)
```

`packages/core/src/settle.ts` 한 곳에서 갈린다. `inScope`(금액이 있는 항목)를 `settledItems`
와 `live` 로 나누고, **`pending` · `noTarget` · `billed` 는 전부 `live` 만 본다.**

### 이미 정산한 건은 마감을 막지 않는다

`settled` 인 항목은 결제자가 없어도 **"결제자 미지정"으로 세지 않고**, 대상이 비어 있어도
**"정산 대상 없음"으로 세지 않는다.** 이미 끝난 건이 마감 조건을 막으면 앞뒤가 맞지 않는다.
(현장에서 각자 냈다면 "누가 결제했는가"가 애초에 없을 수도 있다.)

### 실제 결제액에는 남는다

그 사람이 실제로 카드를 긁은 돈이므로 `spent` 에는 그대로 쌓인다. 대신 `paid`(정산 반영액)
에는 안 들어간다. 그래서 둘의 차이가 **항목 단위로 크게 벌어진다.**

여기가 함정이었다. 화면의 `diffNote()` 는 `spent − paid` 를
`기타 인원 몫 + 대상 없는 항목 + 반올림 잔돈`으로 쪼개 설명한다. 새 항목을 더하지 않으면
**₩300,000 을 "반올림으로 결제자가 흡수했다"고 적는 거짓말**이 된다.
그래서 `Balance.settled` 를 따로 내보내 그 문장에 한 줄을 더했다.

> 정산 반영액은 실제 결제액에서 **이미 정산한 항목 300,000원**, 기타 인원 몫 51,428원,
> 반올림으로 결제자가 흡수한 2원을 뺀 금액입니다.

### 불변식은 그대로다

`paid` 와 `owed` 가 둘 다 `billed` 에서만 나오므로 **잔액 합은 여전히 정확히 0** 이다.
`settle.test.ts` 의 무작위 1000 케이스에 `settled` 를 20% 확률로 섞어 두었다 —
잔액 합 0 · 이체 합 일치 · 전부 정수 세 가지가 그대로 지켜진다.

### 확인이 무효가 되는 것도 그대로 동작한다

항목을 정산 완료로 돌리면 이체 금액이 달라진다. 확인은 금액에 묶여 있으므로
(`docs/decisions/2026-08-20-settle-confirm-amounts.md`) 예전 확인이 자동으로 버려지고
마감이 풀린다. 따로 손댈 것이 없었다.

## 화면

**세 군데서 켜고 끈다. 전부 같은 필드 하나를 쓴다.**

1. **지출 폼** — 정산 대상 아래 체크박스. 정산 토글이 켜져 있을 때만 보인다.
2. **일정 상세 모달** — `정산 완료로 표시` 버튼 한 번. 결제자 지정과 같은 이유로 수정 폼까지 보내지 않는다.
3. **정산 화면 "이미 정산함" 목록** — 줄마다 `정산에 다시 넣기`.

`PATCH /api/groups/:gid/items/:iid {"settled":true}` 하나면 되므로 **새 엔드포인트를 만들지 않았다.**
PATCH 는 보낸 필드만 덮어쓰고, 통화·일차가 그대로면 환율 스냅샷도 유지된다.

**"정산 제외"와 같은 목록에 합치지 않는다.** 앞은 금액이 없는 항목이고 뒤는 금액이 살아 있는
항목이라, 합치면 "왜 이 돈이 합계에 없지?"에 답을 못 한다. 일정 카드에는 금액 옆에 초록 배지를
붙이고, 장부에는 금액 아래 `정산 완료 · 계산에서 빠짐`을 적는다 — 조용히 사라지면 안 된다.

### 이름이 겹치는 문제

이체 한 건의 마지막 단계도 "정산 완료"다. 사용자가 쓴 말이 그것이라 항목 배지에도 같은 말을
썼지만, **목록 제목만은 "이미 정산함"으로 구분**했다. 이체는 사람 사이의 한 건이고 항목은 지출
한 건이라, 같은 화면에서 제목까지 같으면 무엇이 끝난 것인지 알 수 없다.

## 한계 — 항목 단위다, 사람 단위가 아니다

4명이 나눠 내는 식사에서 **2명만 그 자리에서 줬다면** 이 기능으로는 표현할 수 없다.
항목 전체가 끝났거나 아니거나 둘 중 하나다.

사람 단위로 하려면 `item_shares` 행마다 확인 플래그가 필요하고, 잔액 계산이 항목×멤버로
쪼개진다. 사용자가 말한 것은 "각 건별로"이고, 실제로 자주 생기는 것은 **한 건이 통째로
끝나는** 경우다. 지금은 항목 단위로 두고, 부분 정산이 실제로 필요해지면 그때 넓힌다.
그때는 `settled boolean` 이 `item_shares.settled_at` 으로 내려가고 이 컬럼은
"전원이 끝났다"의 파생값이 된다 — **되돌리는 비용은 마이그레이션 한 벌이다.**

## 뒤집는 비용

- **기능 자체를 없애기** — `settle.ts` 에서 `live` 를 지우고 `inScope` 로 되돌리면 계산은 원래대로다.
  컬럼은 남겨 둬도 무해하다 (CHECK 가 `split` 없는 곳에는 못 붙게 막는다).
- **DB** — `005_item_settled.sql`. 컬럼 하나 + CHECK 하나. `DEFAULT false` 라 기존 행은 전부 그대로다.
- **API 계약** — 필드만 늘었다. `settledTotal` · `settledItems` · `balance[].settled` 는 추가이고
  기존 필드의 뜻은 하나도 바뀌지 않았다. 다만 **`total` 에서 정산 완료 항목이 빠진다** — 이건 의도다.

## 정산 뷰어(외부 공유)는 건드리지 않았다

`/{groupId}/settle/{token}` 은 이름·금액·이체 목록만 보여 준다. 이미 끝난 건은 **주고받을 것이
없으므로** 외부인이 볼 이유가 없다. `total` 이 자동으로 줄어드는 것으로 충분하다.
항목 제목이 밖으로 나가지 않는다는 기존 규칙도 그대로다.

## 검증

```
web   130건 통과 — 두 목록을 안 합치는지, 되돌리기가 settled 한 필드만 보내는지
프로토타입      1,658,570 → (28,000 정산 완료) → 1,630,570, 잔액 합 0, 전부 정수
```
