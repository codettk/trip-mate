# 시각은 전부 한국 시간이다 — 두 겹으로 어긋나 있던 것

2026-08-23. 사용자 지적: **"앨범에 시간을 보니까 한국 시간이 아닌 거 같아. 한국 시간으로 업로드시간과 촬영시간이 보이게해줘"**

## 증거

파일 이름이 카메라의 벽시계를 그대로 갖고 있어서 판정이 쉬웠다.

```
파일명            20260822_194244   ← 카메라가 19:42 라고 찍었다
DB 를 UTC 로 읽으면        19:42    ← 파일명과 일치
DB 를 한국 시간으로 읽으면 04:42    ← 9시간 밀렸다
```

## 어긋난 곳이 둘이었다

### ① 서버 — EXIF 를 기계의 시간대로 읽었다

```ts
const when = new Date(tag.DateTimeOriginal);   // "2026:08:22 19:42:44"
```

**EXIF 촬영 시각에는 시간대가 없다.** 카메라가 가리키던 벽시계 숫자일 뿐이다.
그걸 `new Date()` 에 넣으면 **그 코드가 돌아가는 기계의 시간대**로 해석된다.
개발 PC 는 KST, Render 는 UTC — 같은 사진이 어디서 업로드되느냐에 따라 9시간 다르게 저장됐다.

`exifr` 은 기본값이 `reviveValues: true` 라 날짜를 알아서 `Date` 로 되살리는데,
되살리는 그 순간 시간대가 기계에 묶인다. 그래서 **`reviveValues: false` 로 끄고 원문 문자열을 받는다.**

### ② 화면 — 보는 사람 기기의 시간대로 찍었다

```ts
`${d.getMonth() + 1}.${d.getDate()} ${d.getHours()}:${d.getMinutes()}`
```

`getHours()` 는 **브라우저가 놓인 기기의 시간대**를 따른다. 같이 보는 앨범인데
서울에서는 19:42, 해외에서 열면 다른 숫자가 적힌다. "언제 찍은 거야"를 이야기할 수 없다.
사용자가 지금 해외에 있어서 이 부분이 먼저 눈에 띄었다.

**두 결함이 서로를 가리고 있었다.** 개발 PC(KST)에서는 ①과 ②가 상쇄돼 맞아 보였다.
Render 에 올린 뒤에야 드러났다.

## 정한 것 — 시간대를 기계에서 떼어낸다

**`packages/core/src/tz.ts` 한 곳에만 규칙을 둔다.** 서버와 브라우저가 같은 함수를 부른다.

| 함수 | 쓰는 곳 |
|---|---|
| `kstStamp` | `08.22 19:42` — 사진 목록·라이트박스 배지 |
| `kstDateTime` | `2026.08.22 19:42` — 문서 수정 시각 |
| `toKstInput` / `fromKstInput` | `datetime-local` 입력칸 (읽기·저장 **양쪽 다**) |
| `exifInstant` | EXIF 문자열 → 실제 순간 |

KST 는 서머타임이 없어 offset 이 **항상 `+09:00`** 이다. 계산이 단순해지고 경계 사례가 없다.

### EXIF 해석 규칙

- `OffsetTimeOriginal` 처럼 **시간대가 적혀 있으면 그것을 믿는다.** 진짜 순간을 알 수 있다.
- 없으면 **한국 시간으로 친다.** 그러면 화면(한국 시간)에 카메라가 보여 준 숫자가 그대로 돌아온다.

일본도 `+09:00` 이라 이번 후쿠오카 여행에서는 어느 쪽이든 결과가 같다.
시차가 있는 곳에서 찍은 사진은 **"그 순간의 한국 시간"** 으로 보인다 — 사용자가 요청한 것이 그것이다.

## 왜 "기기 시간대"가 아니라 "한국 시간"인가

여행지 현지 시각으로 보여 주는 선택지도 있었다. 고르지 않은 이유:

- **모임은 여러 명이 같이 본다.** 기기 시간대를 따르면 같은 사진에 사람마다 다른 시각이 적힌다.
- **여행지 시간대를 저장하고 있지 않다.** 모임에는 여행지 이름(`dest`)만 있고 시간대가 없다.
  추론해서 넣으면 틀렸을 때 조용히 틀린다.
- 사용자가 명시적으로 한국 시간을 요청했고, 이 서비스는 한국에서 쓰는 서비스다.

나중에 현지 시각이 필요해지면 `Group` 에 시간대를 하나 넣고 `tz.ts` 의 상수를 인자로 바꾸면 된다.

## 이미 저장된 값을 고쳤다

Neon 에 있던 사진 13장 중 촬영 시각이 있는 **10장 전부**가 UTC 로 저장돼 9시간 밀려 있었다.
파일명(`YYYYMMDD_HHMMSS`)과 대조해 판정한 뒤 `taken_at`을 9시간 되돌렸다.

- 판정은 **분 단위로** 맞췄다. EXIF 와 파일명이 1초 차이 나는 파일이 2장 있었는데,
  초까지 맞추면 그 둘을 "모르는 값"으로 빠뜨릴 뻔했다.
- 되돌린 뒤에는 파일명과 UTC 값이 더 이상 일치하지 않으므로 **같은 문장을 다시 돌려도 아무 일이 없다.**
- `uploaded_at` 은 원래부터 `timestamptz` 라 순간이 정확했다. **화면 표시만 틀렸다** — 데이터는 안 건드렸다.

## 검증

시간대 버그는 "내 기계에서는 맞아 보인다"가 가장 위험하다. 그래서 **테스트를 다른 시간대에서 돌렸다.**

```
core 95건 · web 사진 14건 → TZ=UTC / America/New_York / Asia/Seoul / Pacific/Kiritimati 전부 통과
```

특히 `2026-08-22T15:30Z` (= 한국 08.23 00:30) 처럼 **날짜가 넘어가는 값**을 골라 고정했다.
예전 코드라면 뉴욕에서 `08.22 11:30` 으로 그려져 곧바로 실패한다.
