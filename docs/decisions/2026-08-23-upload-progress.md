# 업로드 진행률 — 파일마다 몇 %, 전체 중 몇 개

2026-08-23. 사용자 요청: **"미디어 인제스트 시, 미디어별로 몇퍼센트 올라갔고, 전체중에 몇개가 올라갔는지 표기 가능해?"**

## 그때까지의 화면

버튼이 `올리는 중…` 으로 바뀌고, 드롭존에 `업로드 중… 창을 닫지 마세요` 한 줄이 떴다.
그게 전부였다. 40MB 짜리 동영상 하나를 올리면 몇 분 동안 같은 문구만 보인다.

## 왜 그대로는 불가능했는가

두 가지가 동시에 막고 있었다.

**① `fetch` 에는 업로드 진행 이벤트가 없다.**
`fetch` 는 응답 스트림은 읽게 해 주지만 요청 본문이 얼마나 나갔는지는 알려 주지 않는다.
(`ReadableStream` 을 본문으로 넣는 방법이 있지만 `duplex:"half"` 가 필요하고
Safari·Firefox 가 받지 않는다. 우리 사용자는 대부분 휴대폰이다.)

**② 파일 전부가 요청 **하나**에 담겨 나갔다.**
설령 진행률을 받아도 "전체 중 몇 바이트"밖에 알 수 없다. 어느 파일이 지금 올라가는 중인지,
몇 개가 끝났는지는 **원리적으로** 말할 수 없다. 서버가 순서대로 처리하지만 그 사실이
브라우저로 흘러나오는 통로가 없기 때문이다.

## 정한 것

### 파일 하나에 요청 하나

`apps/web/src/screens/Photos.tsx` 가 파일 목록을 받아 **동시에 2개씩** 순서대로 보낸다.

**서버 라우트는 그대로다.** `POST /api/groups/:gid/folders/:fid/photos` 는 원래부터
여러 개도 받고 한 개도 받는다. `docs/API.md` 의 계약도 바뀌지 않았다.
바뀐 것은 브라우저가 그것을 몇 번 부르는가뿐이다.

곁다리로 결함 하나가 같이 없어졌다. 전에는 큰 파일 하나가 413 을 만들면
그 요청 전체가 오류가 되어 **앞서 성공한 파일들의 결과(`uploaded`)까지 화면에서 사라졌다**.
지금은 그 파일 줄만 빨개지고 나머지는 계속 올라간다.

동시 2개인 이유: 무료 티어 서버(Render) 한 대가 받는다. 더 늘리면 서로 느려지기만 한다.
바꾸려면 `UP_AT_ONCE` 한 줄이다.

### XHR 로 보낸다

`api.upload()` 만 `XMLHttpRequest` 를 쓴다 (`apps/web/src/api/client.ts`).
나머지 요청은 전부 `fetch` 그대로다. `xhr.upload.onprogress` 가 유일한 통로다.

### ⚠ 퍼센트는 "브라우저 → 서버" 구간이다

이게 이 결정에서 제일 중요하다.

```
[브라우저] ──① 진행률이 잡히는 구간──> [TripMate 서버] ──② 안 잡히는 구간──> [Google Drive]
```

②는 서버가 EXIF 를 읽고 Drive 로 다시 올리는 시간이다. XHR 은 ①만 안다.
**100% 를 "완료"라고 쓰면 마지막 몇 초가 멈춘 것처럼 보인다** — 특히 동영상에서 길다.

그래서 상태를 다섯 개로 나눴다: `대기 → 보내는 중 N% → 저장 중 → 완료 / 실패`.
`저장 중`이 ②구간이고, 화면에도 한 줄로 적어 둔다:

> 퍼센트는 **서버까지 보낸 양**입니다. 100% 뒤에는 서버가 Google Drive 에 저장하는 시간이 조금 더 걸립니다.

②까지 진짜 진행률을 주려면 서버가 업로드 진행을 따로 저장하고 브라우저가 폴링(또는 SSE)해야 한다.
파일 하나에 요청 하나로 쪼개 둔 지금은 **"몇 개 끝났는가"가 이미 정확하므로** 그 값어치가 크지 않다.

### 전체 막대는 개수가 아니라 바이트 기준

`Σ sent / Σ size`. 개수 기준으로 하면 40MB 동영상 하나와 300KB 사진 하나가 같은 무게가 되어
막대가 절반에서 몇 분씩 멈춘다. 개수는 막대가 아니라 **`3 / 12` 숫자**로 따로 쓴다 —
사용자가 물어본 두 가지가 서로 다른 값이므로 서로 다른 자리에 쓴다.

실패한 파일의 `sent` 는 되돌리지 않는다. 되돌리면 전체 막대가 뒤로 간다.

## 뒤집는 비용

- **한 요청으로 되돌리기** — `Photos.tsx` 의 `send()` 하나. 서버·API 계약은 건드릴 게 없다.
  대신 파일별 퍼센트와 개수 표시를 전부 잃는다.
- **fetch 로 되돌리기** — `client.ts` 의 `upload()` 하나. 진행률을 전부 잃는다.
- **②구간까지 진짜 진행률** — 서버에 업로드 상태 표 + 폴링 엔드포인트가 필요하다. 지금은 안 한다.

## 같이 바뀐 것

- `apps/web/src/test/server.ts` 가 `XMLHttpRequest` 도 가로챈다. **경로 표는 fetch 와 같은 것을 쓴다** —
  가짜 API 를 두 벌 두지 않는다. `manualUploads` 를 켜면 테스트가 진행률과 응답을 직접 굴린다.
- `prototype/index.html` 에 같은 화면을 넣었다(타이머로 흉내). 디자인 정본이 어긋나면 안 된다.
- 전에 따로 있던 "올리지 못한 파일 N개" 상자는 진행 목록 안으로 합쳤다. 규칙을 두 군데 두지 않는다.
