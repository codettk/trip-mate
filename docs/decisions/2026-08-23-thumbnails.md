# 목록과 상세는 원본을 받지 않는다 — Drive 썸네일을 서버가 받아 전달한다

2026-08-23. 사용자 지적: **"썸네일이 아니라 원본을 뷰어하고 있는 거 같아서 엄청 늦게 화면이 띄워지고 있고 ... 상세보기 내에서도 너무 고해상도를 다운받고 있어서 그런지 느린 거 같은데"**

정확한 진단이었다. 실측하면 이렇다.

| 폴더 | 장수 | 폴더 하나 열 때 받던 양 |
|---|---|---|
| 커플 후쿠오카 여행 / 1일차 | 9장 | **41 MB** |
| 커플 후쿠오카 여행 / 2일차 | 2장 | 5 MB |

**작은 사각형 9개를 보여 주려고 41MB 를 받고 있었다.** 해외 모바일에서는 사실상 안 열린다.

## 원인 셋

### ① `/thumb` 경로가 원본을 돌려주고 있었다

```ts
/** 썸네일 — 지금은 트랜스코딩을 하지 않으므로 **원본과 같은 스트림**을 준다. */
app.get("/api/media/:pid/thumb", (req, reply) => serveMedia(req, reply));
```

경로만 미리 열어 두고 내용은 원본이었다. 게다가 **프론트는 그 경로조차 쓰지 않고** `photo.url`
(= 원본)을 직접 깔고 있었다. 껍데기만 있고 아무도 안 쓰는 상태였다.

### ② 동영상은 지연 로딩이 아예 없었다

```tsx
<video src={p.url} preload="metadata" />
```

`<img>` 에는 `loading="lazy"` 가 있었지만 **`<video>` 에는 그런 속성이 없다.**
폴더를 열자마자 모든 동영상이 한꺼번에 연결을 연다. 20MB 짜리 하나만 있어도 목록 전체가 막힌다.

### ③ 상세 보기도 원본이었다

화면에 띄우는 데 4000×2252 원본이 필요하지 않다. 긴 변 1600px 이면 충분하고 12% 크기다.

## 정한 것 — Drive 가 이미 만들어 둔 썸네일을 쓴다

Drive 는 업로드한 파일마다 썸네일을 자동으로 만들어 둔다. `files.get(fields:thumbnailLink)` 로
주소를 받고, 끝의 `=s220` 을 원하는 크기로 바꾸면 그 크기가 나온다. 실측:

| 파일 | 원본 | s400 | s1600 |
|---|---|---|---|
| 20260822_205137.**mp4** | 20.30 MB | **31 KB** (0.1%) | 152 KB |
| 20260822_203815.jpg | 3.11 MB | 38 KB (1.2%) | 430 KB |
| 20260822_194244.jpg | 2.80 MB | 38 KB (1.3%) | 348 KB |

**동영상도 포스터 프레임을 준다.** 그래서 목록에서 `<video>` 를 아예 안 써도 된다 —
②번 문제가 같이 사라진다.

### 왜 우리가 리사이즈하지 않는가

`sharp` 같은 이미지 처리기를 붙이면 네이티브 바이너리(30MB 급)가 들어오고, 업로드마다 CPU 를
쓴다. 지금 서버는 **Render 무료(0.1 CPU · 512MB)** 다. 이미 만들어져 있는 것을 받아 쓰는 쪽이
싸고, 동영상 포스터는 우리가 만들 수도 없다.

기획의 "트랜스코딩은 하지 않는다 — 원본을 그대로 보관한다"와도 어긋나지 않는다.
**원본은 손대지 않고**, 보여 줄 때만 작은 것을 가져다 쓴다.

## ⚠ 썸네일 주소는 인증 없이 열린다

확인해 봤더니 `thumbnailLink` 는 **토큰 없이도 HTTP 200** 이다.

```
(인증 없이 접근: HTTP 200)
```

그러니 그 주소를 브라우저에 내보내는 순간, 묶음에서 뺀 폴더의 사진도 주소만 알면 볼 수 있게 된다.
**원본과 똑같이 서버가 바이트로 받아서 전달한다.** 기존 규칙 그대로다 —
"이미지 자체도 TripMate URL 로 나간다".

썸네일 경로가 권한 검사를 건너뛰지 않는지 테스트로 못 박았다(`folders.test.ts` ⑧).
**유출은 화질과 무관하다.** 줄인 그림으로 보이는 것도 유출이다.

## 429 와 캐시

썸네일을 연달아 받다가 **HTTP 429(요청 제한)** 를 한 번 맞았다. 그래서:

- **못 받으면 `null` 을 주고 원본으로 되돌아간다.** 느릴지언정 사진이 안 보이면 안 된다.
  429·404·형식 오류·`thumbnailLink` 없음을 전부 같은 방식으로 다룬다.
- 받아 온 바이트를 **메모리에 최대 300장** 들고 있는다. 한 장이 30~40KB 라 12MB 남짓이다.
  `thumbnailLink` 는 수명이 짧아 매번 `files.get` 을 다시 해야 하는데, 바이트를 들고 있으면
  그 호출까지 같이 아낀다. 실측으로 **첫 요청 0.9~1.4초 → 캐시 0ms**.
- 응답에는 원본과 같은 `Cache-Control: private, max-age=31536000, immutable` 이 붙는다.
  파일 내용은 바뀌지 않으므로(고치면 id 가 달라진다) 브라우저가 영원히 캐시해도 안전하다.
  **첫 한 번만 느리고 그 뒤는 즉시**다.

### 서버가 잠들면 캐시도 사라진다

Render 무료는 15분 놀면 잠든다. 깨어날 때 메모리 캐시는 비어 있다.
DB 에 넣어 두면 영구적이지만, **"DB 에는 바이너리가 아니라 folderId / fileId 만 저장한다"**
는 확정된 결정을 깨야 한다. 지금은 깨지 않는다 — 브라우저 캐시가 대부분을 흡수하고,
첫 요청 1초는 41MB 를 받는 것과 비교할 게 아니다.

정말 필요해지면 선택지는 둘이다: ① 썸네일을 Drive 에 별도 파일로 올려 `thumb_key` 를 갖는다
(규칙을 안 깬다) ② DB 에 바이트를 넣는다(규칙을 깨야 하므로 승인이 필요하다).

## 크기는 두 개만 받는다

```ts
const THUMB_SIZES = [400, 1600];   // 그리드 / 상세
```

아무 숫자나 받으면 같은 사진이 크기마다 캐시를 따로 차지하고 Drive 요청도 그만큼 늘어난다.
목록 밖의 값은 400 으로 떨어진다 — 400 을 **거절하지 않고 기본값으로 삼는 이유**는,
이상한 값 하나 때문에 사진이 안 뜨는 것보다 조금 다른 크기가 나오는 게 낫기 때문이다.

## 원본은 언제 받는가

- **동영상 재생** — 상세 보기에서 재생을 누를 때만. `preload="none"` 이라 그 전에는 안 받는다.
- 그 외에는 지금 받지 않는다. 원본 다운로드 버튼은 아직 없다.

## 뒤집는 비용

- 프론트만 되돌리려면 `thumbUrl(...)` 을 `p.url` 로 바꾸면 된다 (5군데).
- 서버 경로는 남겨 둬도 무해하다. `thumbnail()` 이 `null` 을 주면 원본이 나간다.
- `local` 드라이버는 원래부터 `null` 을 준다 — **개발 환경은 아무것도 달라지지 않았다.**
